4. LAUNCH TEMPLATE
========================================

The template data includes variables, so it was written as a file outside
the repository rather than quoted inline:

AMI_ID=$(aws ssm get-parameters \
  --names /aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64 \
  --query "Parameters[0].Value" --output text)

USER_DATA=$(base64 -w 0 week6/scripts/day3-user-data.sh)

cat > ~/week6-lt.json <<EOF
{
  "ImageId": "$AMI_ID",
  "InstanceType": "t3.micro",
  "KeyName": "week5-key",
  "SecurityGroupIds": ["$WEB_SG"],
  "UserData": "$USER_DATA",
  "MetadataOptions": {"HttpTokens": "required"},
  "TagSpecifications": [{
    "ResourceType": "instance",
    "Tags": [{"Key": "Name", "Value": "week6-asg-web"}, {"Key": "Week", "Value": "6"}]
  }]
}
EOF

python3 -m json.tool ~/week6-lt.json > /dev/null && echo "valid JSON"

aws ec2 create-launch-template \
  --launch-template-name week6-web-lt \
  --version-description "initial - day3 bootstrap" \
  --launch-template-data file://$HOME/week6-lt.json

Result: week6-web-lt, version 1. Encoded user data was 712 characters.

base64 -w 0 is required. Without -w 0, base64 wraps every 76 characters,
the embedded newlines break the JSON string, and the template is rejected.
run-instances encodes user data automatically; create-launch-template does
not.

HttpTokens required enforces IMDSv2 on every instance the group launches.
The bootstrap script already uses the token flow, so nothing breaks and the
weaker metadata path is closed.

========================================
5. AUTO SCALING GROUP CREATION
========================================

aws autoscaling create-auto-scaling-group \
  --auto-scaling-group-name week6-web-asg \
  --launch-template LaunchTemplateName=week6-web-lt,Version=1 \
  --min-size 2 --max-size 4 --desired-capacity 2 \
  --vpc-zone-identifier "$SUBNET_A,$SUBNET_B" \
  --target-group-arns $TG_ARN \
  --health-check-type ELB \
  --health-check-grace-period 120 \
  --tags Key=Week,Value=6,PropagateAtLaunch=true

Deliberate choices:

Version=1 is pinned rather than $Latest, so a later template change cannot
silently alter what the group launches.

--vpc-zone-identifier takes one comma-separated string, unlike every other
multi-value flag used so far, which take spaces.

--health-check-type ELB, because the default EC2 type only asks whether the
virtual machine is alive. A crashed web server leaves the machine running,
so under EC2 checks the load balancer would stop routing to the instance
while the group kept it, counted it towards desired capacity, and never
replaced it. The result is a zombie: billed, idle, and reported healthy.
ELB checks make the group adopt the load balancer's verdict, so an
application failure self-heals and not just a machine failure.

The command contains no AMI, instance type or instance IDs. The template
describes what an instance is; the group decides how many and where.

========================================
6. FIRST USE OF AUTO SCALING IN THE ACCOUNT
========================================

The first two launch attempts failed:

Failed  Launching a new EC2 instance. Status Reason: Access denied when
attempting to assume role ...AWSServiceRoleForAutoScaling. Validating load
balancer configuration failed.

AWSServiceRoleForAutoScaling is a service-linked role: an IAM role AWS
creates for one of its own services so that service can act in the
account, here to launch instances and register them with load balancers.
It is created automatically on first use of Auto Scaling.

IAM is eventually consistent. The role existed but had not finished
propagating when the group tried to assume it a moment later. This is the
same class of problem as the Day 1 instance profile that run-instances
briefly could not see after creation.

The four roles on the IAM dashboard during the Day 1 audit, all named
AWSServiceRoleFor..., were created by the same mechanism for other
services.

The group then recovered with no intervention:

Failed      11:29:38   Launching a new EC2 instance ... Access denied
Failed      11:29:38   Launching a new EC2 instance ... Access denied
Successful  11:30:40   Launching a new EC2 instance
Successful  11:30:40   Launching a new EC2 instance

Desired capacity was 2 and actual was 0, so the group kept trying until
the two matched. The reconciliation loop was demonstrated before the
exercise designed to demonstrate it.

========================================
7. THE GRACE PERIOD, OBSERVED
========================================

Target health shortly after launch:

INSTANCE_A   unhealthy   Target.FailedHealthChecks
INSTANCE_B   unhealthy   Target.FailedHealthChecks

Then, about a minute later:

INSTANCE_A   healthy
INSTANCE_B   healthy

The instances registered in the target group the moment they launched,
before the bootstrap script had finished installing and starting httpd.
The load balancer began checking immediately and the checks genuinely
failed, which is why the reason is FailedHealthChecks rather than the
initial state.

The 120-second grace period stopped the Auto Scaling group from acting on
that verdict. Without it, the group would have terminated both instances
for not answering HTTP, launched replacements, and those would have failed
the same way: the launch-kill-relaunch loop.

========================================
8. ZONE PLACEMENT
========================================

INSTANCE_A   us-east-1a   InService   Healthy
INSTANCE_B   us-east-1b   InService   Healthy

The subnet list in --vpc-zone-identifier is the set of zones the group may
use, and its standing rule is to keep instances as evenly spread across
them as possible. Two instances across two zones gives one each.

If a zone fails, the group launches the shortfall in a zone that is still
working. When the failed zone recovers, the group rebalances, launching in
the recovered zone before terminating the surplus elsewhere, so capacity
never dips during the correction.

Ten requests through the load balancer split five and five across the two
instances.

========================================
9. SELF-HEALING, AND WHAT IT DOES NOT HIDE
========================================

One instance was terminated directly through EC2, bypassing Auto Scaling,
the way a hardware failure or mistaken click would:

aws ec2 terminate-instances --instance-ids INSTANCE_A

A traffic loop was running in a second terminal at one request every
three seconds:

502 200 504 200 200 200 200 200 200 200 200 200 200 200 200 200

Two client-visible errors.

502 Bad Gateway: the load balancer reached the instance but received a
broken response as httpd was killed mid-request.

504 Gateway Timeout: the load balancer sent a request and nothing came
back, because the instance network was already gone.

Both are load balancer generated errors. They occurred because the load
balancer still believed the instance was healthy and kept routing to it
during shutdown, until two failed checks at 15-second intervals marked it
unhealthy.

Correction to Day 3: the Day 3 failure test reported ten clean responses,
but that loop ran after the target was already marked unhealthy, so the
window between failure and detection was never measured. A health check
limits the damage of an unexpected failure to its detection window. It
does not eliminate it.

What the group did next:

INSTANCE_NEW   us-east-1a   InService     Healthy
INSTANCE_A     us-east-1a   Terminating   Unhealthy
INSTANCE_B     us-east-1b   InService     Healthy

Successful                        Launching a new EC2 instance: INSTANCE_NEW
WaitingForELBConnectionDraining   Terminating EC2 instance: INSTANCE_A

The replacement went into us-east-1a, the zone that had lost an instance.
The group restored balance, not just the count.

The replacement was launched before the old instance finished terminating.
Restoring capacity comes first and cleanup second.

The group ran its standard termination procedure on an instance that was
already dead: deregister, wait for connection draining, then terminate.
Here it was ceremony. When the group terminates an instance itself, the
same step is what prevents the 502 and 504 seen above.

Nothing was repaired. The group compared what existed with what was
declared and closed the difference.

========================================
10. DEREGISTRATION DELAY
========================================

The terminated instance sat in Terminating for several minutes because the
target group's deregistration delay defaults to 300 seconds. That default
would slow every subsequent scale-in, refresh and teardown the same way.

aws elbv2 modify-target-group-attributes --target-group-arn $TG_ARN \
  --attributes Key=deregistration_delay.timeout_seconds,Value=30

For a page that responds in milliseconds, 30 seconds is ample. The trade
is that a shorter delay cuts off long-running requests.

The instance already draining continued to run out the original delay.
The new value applies to deregistrations that start after the change.

11. INSTANCE REFRESH
========================================

The order of the remaining exercises was swapped. Scaling on CPU needs CPU
metrics, and version 1 of the template did not enable detailed monitoring,
so EC2 reported CPU only every five minutes. A new template version gave a
real reason to deploy: one-minute metrics, plus a version marker on the
page so each instance's origin is visible.

New bootstrap script committed as week6/scripts/day4-user-data.sh, adding
the line <p>Template version: 2</p>.

Version 2 inherits everything from version 1 and changes two fields:

cat > ~/week6-lt-v2.json <<EOF
{
  "UserData": "$USER_DATA_V2",
  "Monitoring": {"Enabled": true}
}
EOF

aws ec2 create-launch-template-version \
  --launch-template-name week6-web-lt \
  --source-version 1 \
  --version-description "v2 - detailed monitoring, versioned page" \
  --launch-template-data file://$HOME/week6-lt-v2.json

The version pin, proven:

Group launch template:   week6-web-lt   1
Page version lines:      0

Version 2 existed and nothing had changed. Creating a template version
deploys nothing.

Pointing the group at version 2 also deploys nothing to running instances;
it changes only what the next launch looks like:

aws autoscaling update-auto-scaling-group --auto-scaling-group-name week6-web-asg \
  --launch-template LaunchTemplateName=week6-web-lt,Version=2

The rollout:

aws autoscaling start-instance-refresh --auto-scaling-group-name week6-web-asg \
  --preferences '{"MinHealthyPercentage": 100, "MaxHealthyPercentage": 200, "InstanceWarmup": 120}'

MinHealthyPercentage 100 with MaxHealthyPercentage 200 means launch the new
instance first, wait until it is healthy and warmed up, and only then
retire an old one. Capacity never dropped below 2. This requires room to
grow, which is what the maximum size of 4 provided.

Traffic during the refresh, status code and template version per request:

200:v1 (x30) ... 200:v2 200:v2 200:v1 200:v2 200:v2 200:v2 200:v2 200:v2
200:v1 200:v1 200:v1 200:v1 200:v1 200:v2 200:v2 200:v2 200:v1 200:v2
... 200:v2 (remaining)

Sixty requests, sixty 200 responses.

Why no errors here when the direct termination produced two: the Auto
Scaling group did the removing, so it launched the replacement first,
deregistered the old instance, let connections drain, and only then
terminated it. By the time an old instance stopped, the load balancer had
already stopped sending it traffic. Health checks react to a failure;
deregistration means there is no failure to react to.

The mixed stretch matters as much as the clean result. For a period, both
versions served live traffic at the same moment, which is true of every
rolling deployment. Version 2 therefore has to coexist with version 1. Here
that was one line of HTML. In a real system, a version that renames a
database column still read by the previous version breaks every request
that lands on the old instances mid-rollout, which is why schema changes
under rolling deployment are made in backward-compatible steps.

Final status: Successful, 100 percent.

13. WALKING THE PIPELINE WHEN NOTHING HAPPENED
========================================

A few minutes after starting the load, both alarms read OK and desired
capacity was still 2. With two instances pinned at 100 percent the high
alarm should have been heading towards ALARM.

Rather than waiting, the scaling chain was checked from its start: load,
then instance CPU, then the CloudWatch metric, then the alarm, then the
scaling action.

Stage 1, the load itself:

ip-...: 2 yes processes, load: 1.97 1.04 0.44
ip-...: 2 yes processes, load: 1.94 1.04 0.43

The three figures are the 1, 5 and 15-minute load averages. Near 2 on the
1-minute figure means both vCPUs fully busy; a low 15-minute figure means
the load began only minutes earlier.

Stage 2, the metric the policy tracks:

aws cloudwatch get-metric-statistics \
  --namespace AWS/EC2 --metric-name CPUUtilization \
  --dimensions Name=AutoScalingGroupName,Value=week6-web-asg \
  --start-time $(date -u -d '-15 min' +%Y-%m-%dT%H:%M:%SZ) \
  --end-time $(date -u +%Y-%m-%dT%H:%M:%SZ) \
  --period 60 --statistics Average

11:45    0.37
11:50    0.38
11:52    0.35
11:53    0.35
11:54    0.40
11:55    0.38
11:56   65.31
11:57   99.99
11:58  100.00

The pipeline was healthy; the check had simply been too early. The high
alarm needs three consecutive minutes above 50, and CloudWatch data
arrives a minute or two late. At the time of the first check, at most one
high data point existed.

The same output also shows the refresh. The 11:45 and 11:50 rows are five
minutes apart, from version 1 instances on basic monitoring. From 11:52
onwards the rows are one minute apart, from version 2 instances with
detailed monitoring. Under version 1, accumulating three high data points
would have taken fifteen minutes instead of three. The deployment had a
directly measurable effect.

Principle: when the end of a chain does nothing, walk it from the start
and find the first stage that disagrees with expectation.

========================================
14. SCALE-OUT
========================================

ALARM   TargetTracking-week6-web-asg-AlarmHigh-...
4       4

At 11:59:09Z a monitor alarm AlarmHigh in state ALARM triggered policy
cpu-target-50 changing the desired capacity from 2 to 4. At 11:59:18Z an
instance was started in response to a difference between desired and
actual capacity, increasing the capacity from 2 to 4.

The cause text is two sentences describing two separate mechanisms. The
policy never launched anything; it changed one number, desired capacity.
The launching was done by the same reconciliation loop that replaced the
terminated instance in section 9.

Scaling and self-healing are the same engine. Self-healing is reality
falling below the declaration. Scaling is the declaration moving above
reality. Either way, the loop closes the gap.

Why exactly 4. Target tracking scales proportionally:

new capacity = current capacity x (current metric / target)
             = 2 x (100 / 50)
             = 4

The maximum size was also 4, so the calculation and the ceiling agreed.

What 4 actually achieved. The load was pinned to the original two
instances, so after scaling the average became roughly
(100 + 100 + 0 + 0) / 4 = 50 percent: exactly on target, and the group
held steady. But the two original instances were still at 100 percent.
With real traffic the load balancer would spread requests onto the new
instances and every machine would cool down; here the load could not
move, so scaling fixed the number without fixing the problem. An average
metric can be healthy while individual instances are not, which is why
production monitoring also watches the maximum.

The new instances reported WaitingForInstanceWarmup: excluded from the
average while booting, so their near-zero startup CPU could not drag the
average down and trigger an immediate scale-in.

Cost note: a t3.micro is designed for around 10 percent baseline CPU and
earns credits to burst above it. Sustained 100 percent spends beyond the
earned credits, and in the default unlimited mode that surplus is billed
at roughly 5 cents per vCPU-hour. A few cents for this exercise, but the
reason T-family instances are the wrong choice for workloads that run hot
continuously.

========================================
15. SCALE-IN
========================================

Load was stopped early with pkill yes rather than waiting out the timeout.

Scale-in took roughly fifteen minutes to begin. The low alarm requires
fifteen consecutive minutes below 45 percent, against three minutes above
50 for scale-out. Adding capacity late causes an outage; removing it late
costs only money. The asymmetry is deliberate.

12:17:56  AlarmLow triggered: desired 4 to 3, removed an instance in us-east-1b
12:19:43  AlarmLow triggered: desired 3 to 2, removed an instance in us-east-1a

Prediction tested: with two instances in each zone, the termination policy
applies zone balance first, then oldest launch template version (a tie,
all version 2), then closest to the next billing hour (largely meaningless
under per-second billing), then random. Predicted outcome: one removed
from each zone.

Confirmed, with a refinement. Scale-in happened in two separate steps
rather than one. The first step faced a two-two tie and removed from
us-east-1b. The second step faced two in us-east-1a and one in us-east-1b,
and removed from us-east-1a, the more crowded zone. Scale-out jumped from
2 to 4 in one decision; scale-in removed one instance at a time and
re-evaluated in between.

One of the removed instances was one of the two that had run the load.
CPU history plays no part in the choice.

========================================
16. TEARDOWN AND THREE STRAGGLERS
========================================

The group must go first. Terminating its instances while it exists only
causes it to launch replacements.

ASG_IDS=$(aws autoscaling describe-auto-scaling-groups --auto-scaling-group-names week6-web-asg \
  --query "AutoScalingGroups[0].Instances[].InstanceId" --output text)

aws autoscaling delete-auto-scaling-group --auto-scaling-group-name week6-web-asg --force-delete
aws ec2 wait instance-terminated --instance-ids $ASG_IDS

The instance IDs were captured before the deletion, because once the group
is gone it can no longer report what it owned.

aws ec2 delete-launch-template --launch-template-name week6-web-lt
aws elbv2 delete-listener --listener-arn $LISTENER_ARN
aws elbv2 delete-load-balancer --load-balancer-arn $ALB_ARN
aws elbv2 wait load-balancers-deleted --load-balancer-arns $ALB_ARN
aws elbv2 delete-target-group --target-group-arn $TG_ARN
aws ec2 delete-security-group --group-id $WEB_SG
aws ec2 delete-security-group --group-id $ALB_SG

Every command reported success except the last, and the first
verification pass still found three resources.

The load balancer security group failed with DependencyViolation, has a
dependent object. Not the web tier rule, which had been deleted a line
earlier. The dependent object was identified rather than guessed:

aws ec2 describe-network-interfaces --filters Name=group-id,Values=$ALB_SG

A load balancer is physically a set of network interfaces in the subnets.
The waiter reports the load balancer deleted while its interfaces are
still being released, and they hold the security group until they are
gone. By the time the query ran they had been released, and the retried
deletion succeeded.

The Auto Scaling group was still listed. --force-delete starts an
asynchronous deletion that completes after the instances terminate. A
later status query returned nothing, meaning the group no longer existed.

The two target tracking alarms were still present after the group was
gone, and were deleted directly:

aws cloudwatch delete-alarms --alarm-names $(aws cloudwatch describe-alarms \
  --alarm-name-prefix TargetTracking-week6 --query "MetricAlarms[].AlarmName" --output text)

Resources a service creates on the account's behalf do not always
disappear on the same schedule as the thing that created them.

Final verification across Auto Scaling groups, launch templates,
target tracking alarms, load balancers, target groups, instances, week6
security groups and available volumes: all empty.

Principle, arriving by a different route than on Day 2: in AWS, deleted
often means deletion has started. Only the listing afterwards confirms the
state.

Key Learnings:
- A 503 from an ALB with no healthy targets is generated by the load
  balancer, not the application
- EC2 health checks cannot see a crashed application; ELB checks can
- First use of a service can fail on a service-linked role that has not
  finished propagating; the group retries by itself
- A health check limits an unexpected failure to its detection window;
  only deregistration avoids client errors entirely
- Creating a template version, and pointing the group at it, both deploy
  nothing; an instance refresh is the deployment
- During any rolling deployment two versions serve traffic at once
- Detailed monitoring turns a fifteen-minute scaling reaction into three
- A scaling policy only changes desired capacity; the same reconciliation
  loop does both scaling and healing
- An average can sit on target while individual instances are saturated
- Scale-out is fast and in one step; scale-in is slow and one instance at
  a time
- Deletions are often asynchronous: interfaces, groups and managed alarms
  can outlive the command that removed their owner
